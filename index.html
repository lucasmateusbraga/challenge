Foundey · Senior PD Challenge

From parallel blocks to a single priority queue

Redesign of the internal fulfillment operations dashboard so opening the screen immediately answers: what do I need to do now?

Context: internal ops app (fulfillment) Time: < 1h Deliverable: reasoning + wireframe
01 · The problem

The dashboard gives everything the same weight, so nobody knows where to start

Today the screen combines recent activity, orders, notifications, and team comms into four parallel blocks. None of them says which item is more urgent than another, so people have to open all four to find out.

"I never know what needs my attention first." Recurring dashboard user complaint

From the manager side: "I cannot see what each team member is working on." Both problems come from the same root cause: the screen organizes by content type, not by what requires action now.

02 · Design principle

A queue ordered by real urgency, not a wall of sections

The system decides where to start, not the person.

This is not about adding another filter to the current screen. It assumes orders, notifications, and comms compete for the same attention, so they need to be compared against each other using a visible criterion, not simply listed side by side.

One queue, not four blocks

Actionable items from every source enter the same ordered list.

Visible criterion

Each item shows why it is in that position (deadline, impact).

Reference does not compete with action

Anything that does not require a decision stays visually below, without competing for space.

03 · Decisions

Three choices that define the screen

Decision 01 · Structure

One queue across types instead of blocks by type

Tension: grouping by type (orders, notifications, comms) is easier to scan within each category, but forces people to decide which block to open first.
Option A

Keep the four content-type blocks and only reorganize them visually.

Option B - selected

One section, "Needs Your Attention", that gathers items requiring action and orders them by urgency, with a label showing each item's source.

Why: the issue is not a lack of information. It is a lack of order among information that already exists. Separating by type improves scanability, not prioritization.
Tradeoff: each type has less context at a glance. That is why the source label (Order / Notification / Comms) remains visible on each row.
Decision 02 · Urgency criterion

Deadline and impact, not arrival order

Tension: "urgent" can mean creation date, deadline (SLA), or order/customer impact, and each data source speaks a different language today.
Option A

Sort by creation date, newest first. This mirrors the current "Recent Activity" pattern.

Option B - selected

Sort by a compound criterion: at-risk deadline > order/customer impact > wait time. The deadline appears on each row ("due 2h ago", "due today").

Why: creation date says nothing about risk. An order that has been blocked by payment for 1 hour is more urgent than a 3-day-old notification with no deadline.
Tradeoff: this criterion assumes each source has, or will have, a deadline/severity field. That is a data dependency, not just a layout dependency, and remains an open assumption.
Decision 03 · Manager view

Same dashboard, regrouped by person

Tension: managers need to see team workload, but a separate screen doubles maintenance and creates two sources of truth.
Option A

Separate manager-only screen with its own team view.

Option B - selected

A "Queue / By person" toggle on the same dashboard: managers can regroup the same queue by team member.

Why: the queue and urgency criteria already exist. Regrouping is cheaper than rebuilding, and the manager sees exactly the same source the team uses.
Tradeoff: per-person workload metrics (item count, average time) do not fit this simple regrouping and are outside the scope of this design.

From sketch to final UI: the single queue and the "action vs. reference" separation from the design principle remain. Only the visual language changes: a color dot replaces the colored block, and a subtle label replaces the large tag. No new prioritization logic or workload metrics were introduced in this transition; the high-fidelity screen uses representative content to demonstrate the final layout and interactions.
05 · Solution · high-fidelity UI

The same queue, now with polished craft

The same priority queue concept from the sketch, now expressed as a polished UI. Four items appear as cards in the first viewport, with two additional representative examples available through "View all 6 items". The deadline pill uses the same visual language as the urgency system, and "By person" is Decision 03: the queue regrouped by owner.

06 · What was left out

Assumptions and limits of this 1-hour design

  • - The urgency criterion assumes deadline/impact can be calculated today by each source (orders, notifications, comms). In practice, this may require a data change, not just a screen change.
  • - Per-person workload metrics for the manager (item count, average resolution time) were not designed. The toggle only regroups the existing queue.
  • - Empty states and push notifications were not designed. The focus was the priority hierarchy of the main screen. The mobile version was treated only as a viewing adaptation of the same UI, without creating a new experience or flow.
  • - "Customer/order impact" is treated here as a single signal. In production, it will likely be composed of more than one variable and should be validated with real support data.
